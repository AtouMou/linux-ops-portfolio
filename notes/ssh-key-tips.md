# SSH 密钥 & Git 推送踩坑笔记

> 2026-07-24 整理：调试 GitHub SSH 推送时学到的关键知识点

---

## 一、SSH 密钥对的基本原理

| 文件 | 类型 | 谁能看 |
|------|------|--------|
| `id_ed25519` | 私钥（private key） | **只有自己**，绝对不能给任何人 |
| `id_ed25519.pub` | 公钥（public key） | 可以给任何服务（GitHub、服务器等） |

**工作原理**：

```
你（持私钥）  ──用私钥签名──>  GitHub（持公钥）
                                      ↓
                              验证签名 → 匹配 → 通过
```

公钥可以被任意多个服务信任，**私钥只有自己持有**。

---

## 二、ssh-keygen 的关键提示

执行 `ssh-keygen -t ed25519 -C "email"` 时会出现三个提示：

```
Enter file in which to save the key (/root/.ssh/id_ed25519):  ← 直接回车
Enter passphrase (empty for no passphrase):                    ← 建议设密码
Enter same passphrase again:                                   ← 重复输入
```

### 血泪教训

> **不要乱输入文件名！提示里括号里的路径是默认值，直接回车就行。**

如果输入 `1` 这种字符：

- 不会保存到 `~/.ssh/`
- 会保存到**当前工作目录**下的 `1`（私钥）和 `1.pub`（公钥）
- 如果当前目录正好是 git 仓库，`git add .` 会**无差别收集全部文件**
- 私钥就被 commit 推到了 GitHub ⚠️

## 三、企业里 SSH 密钥怎么分配？

### 核心原则

> **企业不分配私钥，只收集公钥。私钥永远是私人的。**

### 常见方案

| 方案 | 做法 | 适用场景 |
|------|------|----------|
| 方案一：员工自生成 | 员工自己 `ssh-keygen`，把公钥交给运维 | 初创 / 小团队（最常见） |
| 方案二：CA 签发证书 | 公司当 CA，给员工公钥签名 | 中大型企业 |
| 方案三：跳板机 + IAM | 员工先登跳板机，再分发临时密钥 | 安全要求高 |
| 方案四：SSO + 动态密钥 | Vault / AWS Session Manager 颁发 4 小时有效密钥 | 最现代 |

### 一个公钥可以配多个服务

✅ **对**。一个公钥可以给 GitHub、GitLab、公司服务器、AWS 等无数个服务信任。

### 私钥能"分发"吗？

❌ **不能**。私钥一旦离开你的机器，就视为已泄漏，必须重新生成。

## 四、覆盖现有 SSH 密钥会怎样？

### 场景

`~/.ssh/id_ed25519` 已经存在，再跑一次 `ssh-keygen`，直接回车覆盖。

### 结果

- 本地私钥变成新密钥
- 但 GitHub 上还存着旧公钥
- 新私钥签名 → 旧公钥无法验证 → **认证失败**，但**链接不会丢**

### 恢复方法

1. **方向 A**：拿回旧公钥，重新加到 GitHub（前提是旧私钥没被覆盖）
2. **方向 B**：直接用新密钥，把新公钥加到 GitHub

> 哪个密钥能继续用，取决于哪个密钥被 GitHub 信任，本地覆盖不会"通知" GitHub。

## 五、私钥泄漏的应急处理

### 严重程度分级

| 场景 | 严重程度 |
|------|----------|
| 公开仓库 + 泄漏的密钥未绑任何服务 | 🟡 中（攻击者拿 key 也没用） |
| 公开仓库 + 密钥绑了 GitHub 账号 | 🔴 严重（账号可被冒用） |
| 仓库里有其他密钥、密码 | 🔴🔴 高危 |
| 密钥还用在服务器、其他平台 | ⚫ 灾难级 |

### 应急步骤（标准流程）

1. **立刻去 GitHub 删除对应公钥**（让旧密钥失效）
2. **从 Git 历史彻底清除**：`git filter-repo --invert-paths --path 1 --path 1.pub`
3. **强制推送重写历史**：`git push origin --force --all`
4. **重新生成密钥**：`ssh-keygen -t ed25519 -C "email"`（直接回车走默认路径）
5. **加载新密钥**：`eval "$(ssh-agent -s)" && ssh-add ~/.ssh/id_ed25519`
6. **新公钥加到 GitHub**，测试 `ssh -T git@github.com`
7. **更新 `.gitignore`**：加 `*.pem`、`*.key`、`id_*`、`*.pub` 防护

### 易踩的坑

| 命令 | 错在哪里 |
|------|----------|
| `git revert <commit>` | 不能从历史抹掉文件，只是新增一个反向 commit |
| `git reset <commit>` | 只移动 HEAD，工作区会乱，不清理文件 |
| `git push --force --all`（没先 filter-repo） | 啥也没清掉 |

> **只有 `git filter-repo`（或 `filter-branch`）能彻底从所有历史 commit 中删除文件。**

## 六、防止密钥泄漏的 `.gitignore` 规则

```gitignore
# 防止密钥泄漏
*.pem
*.key
id_*
*.pub
/private*
```

## 七、SSH 密钥日常管理清单

- [ ] 提示"Enter file"时**直接回车**
- [ ] 敲 `git add .` 前先 `git status` 看一眼
- [ ] 私钥文件**绝不提交**到任何仓库
- [ ] 同一密钥不要在多个设备上裸拷（用 ssh-agent 转发更安全）
- [ ] 离职前删除 GitHub 上的公钥（如果是公司分配的 key）
- [ ] 怀疑泄漏就当泄漏处理：删公钥 + 重新生成 + 清理历史
